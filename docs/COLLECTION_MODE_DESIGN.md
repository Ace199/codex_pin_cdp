# Chat Pin 采集模式设计方案

> 状态：0.9.0 将采集从“生成聚合文档”改为“按规则实际修改当前任务工作区”；真实 Codex Desktop + 独立 CLI 端到端复验仍待完成
>
> 日期：2026-08-25
>
> 首版版本：0.8.0

### 当前实施摘要

已实现：独立 CLI 检测、App Server JSONL 客户端、每项新 thread、规则快照、单并发持久化队列、当前工作区受限写入、采集/修订互斥、原生发送拦截和执行报告反馈。

尚未验证：真实 Codex Desktop + 独立 CLI 对资料库项目的完整端到端写入，以及 Windows/macOS 在受管权限策略下的行为。下文以 0.9.0 的执行式采集为当前基线；0.8.x 的聚合结果文件仅作为历史说明。

### 0.8.1 修正

- 发送拦截覆盖 `pointerdown`、`mousedown`、`click`、表单 `submit` 和 Enter，多个事件收敛到同一次入队，防止采集请求同时进入当前 Desktop 对话。
- “采集”扩展到所有原生 Markdown 文件页，位于“查看源代码”左侧；Pin 文件页仍保留“采集 / 修订 / 查看源代码”的顺序。普通规则文件必须能在当前工作区内按文件名唯一定位，同名歧义时拒绝启用。
- App Server 仍优先使用官方当前的 `readOnly` 字段；实际 CLI 明确返回旧枚举错误时，兼容回退到 `read-only`。

### 0.8.2 修正

- 不再区分 Pin 打开与普通文件打开。点击任意 Markdown 文件页上的“采集”后，该文件直接成为当前采集规则。
- 从另一个规则文件切换过来时不再显示二次确认；再次点击同一个文件的“采集中”才关闭采集模式。
- 普通 Markdown 与 Pin 文件共用同一套显性状态：文件页按钮高亮显示“采集中”，输入框上方持续显示当前规则文件名和队列状态。
- 切换只影响后续输入；已加入队列的项目继续使用入队时保存的规则文件快照。

### 0.8.3 修正

- 采集发送不再只依赖 `preventDefault`。捕获发送意图后先同步读取并清空原生输入框，再请求启动器入队，使后续原生发送逻辑无法取得原消息。
- 入队失败时，仅在输入框仍为空的情况下恢复原输入，避免覆盖用户已经输入的新内容。
- 发送监听提升到 `window` 捕获阶段并覆盖 `pointerup`；短暂提交锁避免同一次鼠标操作重复入队。
- 状态栏显示持久化队列中的失败数量，避免把“没有待处理项但存在失败项”仅显示为“队列空闲”。

### 0.8.4 修正

- `thread/start.sandbox` 与 `turn/start.sandboxPolicy.type` 分别协商 camelCase/kebab-case，不再把一次回退错误地复用到另一字段。默认仍遵循官方当前的 `readOnly`。
- 采集启用期间，原生发送按钮不再接收指针事件；Chat Pin 根据按钮位置接管点击并入队，避免 Codex 较早注册的监听器先发送到主任务。
- 入队失败后的输入恢复延迟到本次鼠标/键盘事件链结束，并且仍只在输入框为空时恢复。

### 0.8.5 修正

- 绿色状态栏在存在失败项时显示“重试”，将全部失败项按各自保存的原输入和规则快照恢复为待处理状态；已经完成或仍在等待的项目不受影响。
- 状态栏提供“清空”，移除当前会话的全部队列记录，但不关闭采集模式，也不删除已经写入的聚合结果文件。
- 清空会递增队列 generation。若某项已经交给 CLI 且无法中断，其迟到结果会因 generation 不匹配而被丢弃，不能继续追加到结果文件。

### 0.8.6 修正

- App Server 的 `error` 通知带有 `willRetry: true` 时，不再立即把采集项标记失败或调用 `turn/interrupt`，而是继续等待 CLI 自动重连、传输降级或最终 `turn/completed`。
- `willRetry` 缺失或为 `false` 的错误仍按终止错误处理；最终非完成状态和总超时仍会失败，避免吞掉真实错误。
- 增加假 App Server 回归测试，分别覆盖可恢复重连后成功以及不可重试错误继续失败。

### 0.8.7 修正

- 采集模式从“按渲染页保存”改为“按任务 ID 保存”，并把启用状态、规则文件路径和启用时间写入对应队列文件。切换到其他任务再返回、注入重载或启动器重启后，会在规则文件仍存在时恢复该任务的采集模式。
- 绿色状态栏持续显示已完成数量，并在已有结果时提供“查看结果”。结果仍不伪装成当前任务的原生助手回复。
- “查看结果”复用 Codex 原生 Markdown 文件打开状态机；当前任务使用其他工作区时，先把最新结果复制到该工作区的 `collections/` 镜像再打开。

### 0.8.8 修正

- 启动器在采集状态中公开协议版本和能力列表；注入脚本只有在确认 `open-result` 能力后才显示“查看结果”。
- 当注入脚本已经热更新但后台启动器仍为旧进程时，界面明确提示重启，不再调用旧启动器并得到“未知采集操作”。

### 0.8.9 修正

- 采集结果主文件改为 `<当前任务工作区>/collections/collection_<sessionId>.md`，不再默认写入 Chat Pin 插件仓库。队列 JSON、重试状态和 App Server 标识等运行元数据仍由独立 profile 管理。
- 每个新采集 thread 的 `cwd` 改为入队时确认的任务工作区，仍使用只读 sandbox；任务工作区路径随队列项保存，避免切换任务后执行到错误项目。
- 首次启用或恢复旧任务时，如果插件仓库中存在旧结果而项目新位置尚不存在，则安全复制旧结果；不自动删除旧文件，也不覆盖项目中已有结果。
- 项目内结果文件通过 `.git/info/exclude` 本地保护，不修改项目 `.gitignore`；点击“查看结果”时临时解除索引排除并在打开后恢复。
- 当前任务输入框上方显示明确标注为“本地”的采集结果卡片；切换任务再返回时从项目聚合 Markdown 恢复最近结果。卡片不是原生助手消息，也不会进入模型上下文。

### 0.9.0 变更

- 采集规则文件从“输出格式参考”提升为必须落实的工作流程。规则要求建立来源记录、更新索引或执行验证时，CLI 必须实际修改当前任务工作区，不能只返回一篇建议写入的 Markdown。
- `thread/start.sandbox` 与 `turn/start.sandboxPolicy.type` 改为 `workspaceWrite`，并把 `writableRoots` 限定到入队时的任务工作区；旧 CLI 仅在明确返回枚举错误时回退到 `workspace-write`。
- 不再新建或追加 `collections/collection_<sessionId>.md`。旧聚合文件不删除、不迁移、不覆盖；队列状态和简洁执行报告保留在插件 profile。
- 输入框上方显示“采集执行报告（本地）”，只报告实际文件改动、验证结果和风险。它不是采集产物，也不进入原生任务上下文。
- 升级时不自动执行 0.8.x 尚未完成的只读队列项；这些项会标为失败并提示用户确认新写入语义后手动重试，避免静默扩大旧任务权限。
- 启用采集只做规则文件、工作区和独立 CLI 路径检查，并立即持久化模式；耗时的 CLI 健康探测和 App Server 初始化延后到首个队列项执行。这样冷启动不会让界面的 20 秒请求先超时，也不会留下“界面卡住但队列为空”的半启用状态。
- App Server `initialize` 超时或失败时主动结束本次创建的子进程，防止残留进程影响后续重试。
- “清空”除递增 generation 和删除记录外，还会取消当前运行项并向 App Server 发送 `turn/interrupt`；即使中断响应迟到，旧任务也不能继续占用单并发队列或写回当前状态。中断前已经发生的工作区文件修改仍不会自动回滚。
- 鼠标发送不再让事件直接命中 Codex 原生发送按钮：采集模式在原按钮位置挂载独立透明覆盖按钮，原按钮禁用指针命中，由注入器从覆盖按钮接管入队。Enter 和表单提交仍在 `window` 捕获阶段阻断，防止同一输入同时进入 CLI 与原生 Desktop 对话。

### 0.9.1 与 0.9.2 修正

- 待处理期间每 2 秒校准队列状态，绿色状态栏区分准备/预处理、独立任务启动和独立 CLI 执行，并显示耗时；报告展开状态不再因无关 DOM 刷新丢失。
- 原生发送按钮除禁用指针命中外，还设置真实 `disabled`。输入事件与 React DOM 替换后立即重建按钮保护和透明覆盖层，不等待通用刷新节流，从而关闭重渲染后同一输入进入 CLI 与 Desktop 的竞态窗口。
- 每个队列项在入队时快照 Desktop 输入框旁当前可识别的模型和推理强度，交给独立 CLI 执行。显式环境变量优先；模型标签不可识别时才使用自动档位。

### 0.9.3 进度可见性

- App Server 的标准输入输出继续专用于 JSONL 协议，不能直接作为人工交互终端。
- 启动器把关键协议事件转换成现有 CMD 中的可读日志：预处理、模型、App Server/thread/turn、抽样工具事件、文件写入、可恢复重试、上下文压缩和最终状态。
- 执行期间每 20 秒输出一次心跳，包含耗时、阶段、最后活动以及工具/文件计数；不输出完整用户输入或完整模型回答。

## 1. 需求结论

在所有原生 Markdown 文件页的“查看源代码”左侧增加“采集”按钮；Pin 文件页同时保留其右侧的“修订”按钮。开启采集模式后，用户仍在当前 Codex Desktop 任务的输入框中填写要求，但点击发送时不把消息交给当前任务继续生成，而是加入 Chat Pin 自己的采集队列。

每个队列项都以“启用采集时选定的 Markdown 规则文件 + 本次用户输入”为完整业务上下文，通过 Codex CLI 的 App Server 创建一个新的 thread 执行。不同队列项之间不继承历史对话，因此用户可以在同一个桌面任务中连续提交围绕同一规则的采集请求，而不必手动新建多个 Codex 任务。

这里的“无上下文”并不等于模型没有任何上层约束。它准确表示：

- 不读取或继承当前 Codex Desktop 任务的历史消息；
- 不继承前一个采集队列项的用户消息和模型回答；
- 仍受 Codex 的系统规则、账号配置、权限策略以及所选工作区 `AGENTS.md` 等指令约束。

因此，本方案不先“压缩当前对话”再发送。压缩仍会携带历史摘要，不能满足真正的任务隔离；为每个队列项调用一次 `thread/start` 才是更可靠的实现。

## 2. 用户可见行为

### 2.1 开启与关闭

- 按钮名称使用“采集”，放在“查看源代码”左侧；Pin 文件页中位于“修订”左侧。
- 当前打开任意 Markdown 文件时显示；修订仍只对活动 Pin 文件开放。
- 开启后持续显示“采集中”和待处理数量，不能只靠按钮颜色表达状态。
- “采集”和“修订”互斥。开启其中一个时，如另一个已经启用，应先明确提示并关闭旧模式。
- 采集模式按 Codex 任务隔离并持久化。切换到其他任务时只隐藏原任务状态，返回后恢复；不同任务可分别保存自己的采集来源。仅仅打开另一个 Markdown 文件不会改变采集来源；点击该文件页的“采集”后会直接把它设为新来源，不再确认。普通文件与 Pin 文件都在输入框上方显示相同的持续状态栏。未完成队列始终保留并继续使用各自入队时的文件快照。

### 2.2 发送

采集模式开启时，点击原生发送按钮后的顺序为：

1. 读取用户输入，但不把隐藏指令写入输入框。
2. 阻止本次消息进入当前 Codex Desktop 对话。
3. 将原始输入、当前规则文件快照及目标工作区组成队列项。
4. 在原生发送事件链继续前同步清空输入框，再请求启动器入队；入队失败时仅在输入框仍为空的情况下恢复原输入。
5. 后台逐条执行；队列状态包括“等待、执行中、完成、失败”，失败项可从绿色状态栏重新排队。
6. CLI 按规则实际修改并验证当前工作区；最终文本只作为本地执行报告，绿色状态栏持续显示已完成数量，不伪造原生助手消息。

如果加入队列失败，必须保留输入框内容，避免用户要求丢失。

### 2.3 为什么不把采集请求继续发到原生对话

只在输入中追加“忽略之前的对话”不能保证模型不使用当前任务历史。插件也没有受支持的接口去清空 Codex Desktop 当前任务的内部上下文。

因此采集模式必须截住原生发送，改由 CLI/App Server 独立执行。如果同时发送给原生任务和 App Server，就会产生两份回答，也无法实现上下文隔离。

## 3. 总体架构

```text
Codex Desktop 输入框
  -> 运行时注入器截获采集发送
  -> Runtime binding 传给 pin-launcher
  -> 本地持久化队列
  -> Codex CLI: codex app-server
  -> 每个队列项 thread/start（全新对话）
  -> turn/start（Pin 快照 + 本次输入）
  -> workspaceWrite 在当前任务工作区执行规则
  -> 文件写入、索引更新和规则要求的验证
  -> 启动器持久化简洁执行报告
  -> 注入器更新队列状态/显示执行报告
```

职责分工：

| 组件 | 职责 | 不负责 |
| --- | --- | --- |
| `inject/codex-pin.user.js` | 按钮、状态展示、截获发送、提交队列、错误提示 | 启动 CLI、保存认证信息、直接执行模型请求 |
| `scripts/pin-launcher.mjs` | CLI 发现、App Server 生命周期、队列、规则快照、执行报告持久化 | 修改 Codex 安装包、读取桌面对话数据库 |
| Codex App Server | 新建 thread、执行 turn、流式返回事件、处理 Codex 权限模型 | 保存 Chat Pin 的产品状态 |
| 本地采集存储 | 保存队列、输入、Pin 哈希、输出及诊断信息 | 保存访问令牌或 Cookie |

## 4. CLI 检测与启动

### 4.1 不能只检查文件是否存在

Windows 的 Microsoft Store Codex Desktop 包内可能存在 `resources/codex.exe`，但 Node 直接启动它可能返回 `EPERM`。这类路径不能仅凭 `where codex` 的结果认定为可用 CLI。

启动器应按以下顺序解析：

1. 用户显式配置的 `CODEX_PIN_CLI_PATH`；
2. 当前 `PATH` 中可执行的 `codex`，Windows 同时检查 `codex.cmd`；
3. npm、Homebrew 等常见安装位置；
4. 都不可用时停止启用采集模式，并显示安装/修复提示。

桌面包内的 bundled CLI 不作为默认回退。启用时先确认候选路径存在；完整可执行性探测在首个队列项开始时执行，失败项保留原输入与规则快照并显示可重试错误。

### 4.2 两级健康检查

```text
codex --version
codex app-server --help
```

只有两条命令都能正常创建进程并以成功状态退出，才认为采集后端可执行。该检查不阻塞“启用采集”这一 UI 状态转换，而在首个队列项进入执行阶段时完成。若仅第一条成功，任务失败并提示用户升级到支持 App Server 的 CLI 版本；若进程返回 `EPERM`，提示当前命中了桌面包路径，并允许选择独立 CLI。

插件不自动联网安装或升级 CLI，也不自动修改系统 PATH。CLI 缺失时提供官方安装文档入口和“重新检测”按钮。

### 4.3 App Server 生命周期

- 启动器只维护一个 App Server 子进程，使用标准输入/输出上的 JSONL 协议通信。
- 建立连接后先发送一次 `initialize`，收到成功响应后发送 `initialized`。
- App Server 进程可以复用，但 thread 不能跨采集项复用。
- 启动器退出时只终止自己创建的 App Server 子进程，不按进程名批量结束其他 Codex CLI 或 Desktop 实例。
- 子进程异常退出时，当前执行项标为失败；等待项保留，可在后端恢复后重试。
- `initialize` 超时或失败时必须终止本次创建的子进程，不能把未初始化的进程留给后续任务复用。

官方协议要求每个连接先完成 `initialize`，然后才能调用其他方法；`thread/start` 创建新对话，`turn/start` 在指定 thread 上启动生成。参考 [Codex App Server 官方文档](https://developers.openai.com/codex/app-server/) 和 [Codex CLI 官方文档](https://developers.openai.com/codex/cli/)。

### 4.4 性能预处理与压缩

- 入队时的规则 Markdown 和用户输入必须原样保留，不先经过模型摘要。
- 启动 App Server 的同时，本地脚本提取 URL、日期、Markdown 链接名和 GitHub 仓库 slug；对输入 URL 执行有界的工作区精确查重。
- GitHub 仓库以最多 4 路并发 `HEAD` 请求核验，只保留可达性、HTTP 状态、最终地址和重定向标志。
- 默认跟随本次入队时 Desktop 输入框旁选择的模型与推理强度。若 UI 标签无法识别，常规归档使用 `gpt-5.6-terra` + `medium`；确定性检查识别到安全研究、仓库迁移、重定向或同名冲突时，升级到 `gpt-5.6-sol` + `high`。环境变量可显式覆盖 Desktop 选择或指定 `inherit`。
- App Server 将 `model_auto_compact_token_limit` 设为 100000，范围为 `body_after_prefix`。这会在稳定前缀后的工具上下文增长越过阈值时自动压缩；不把每个采集项强制拆为“先摘要、再写入”两个 turn。
- 执行报告记录预处理、首次工具、首次写入、CLI 和总耗时，以及压缩次数和最后的 token usage。

## 5. 单个采集任务的状态机

```text
读取活动 Pin
  -> 固化 Pin 内容、路径和 SHA-256
  -> 持久化 queued 项
  -> 并行：检查 App Server 健康状态 + 确定性预提取/查重/GitHub 核验
  -> 选择常规或复杂执行配置
  -> thread/start（新的 threadId）
  -> turn/start（原始规则 + 原始输入 + 精简预提取 JSON）
  -> 接收流式事件
  -> 收到 turn/completed
  -> Codex 检查并修改工作区文件
  -> 执行规则要求的验证
  -> 提取最终 agent message 与 fileChange 元数据
  -> 持久化简洁执行报告
  -> 标记 completed
```

任一步失败都要记录明确阶段，不得统一显示“采集失败”。建议的数据结构：

```json
{
  "id": "collect_<timestamp>_<random>",
  "status": "queued",
  "sessionId": "...",
  "workspacePath": "...",
  "pinPath": "pins/pin_<session>.md",
  "sourceHash": "sha256:...",
  "input": "用户本次输入",
  "threadId": null,
  "turnId": null,
  "createdAt": "...",
  "startedAt": null,
  "completedAt": null,
  "error": null
}
```

首版采用单并发 FIFO，避免多个任务同时修改同一索引或来源文件。后续如要并行，必须先设计工作区写入冲突检测，不能简单并发执行。

## 6. 发送给 Codex 的内容

每个新 thread 的首个且唯一一个 turn 包含：

1. 固定的采集约束；
2. 开启采集时的 Pin Markdown 快照；
3. 用户本次输入；
4. 简洁的输出格式要求。

建议模板：

```text
[Chat Pin 采集任务]

你正在执行一个独立采集项。不要使用或假设存在此前的对话或采集结果，
也不要补充本消息未提供且无法可靠确认的信息。

请将“采集目标与处理规则”作为必须落实的工作流程，根据当前输入的数据类型选择合适的处理方式。
输入可能包含单条或批量资料、链接、项目清单、原始数据、交易记录、文章、观点、代码或其他内容，
不要强制套用固定摘要格式。

处理要求：

- 优先服从采集规则中明确规定的字段、分类、格式和输出要求。
- 尽量完整保留有价值的原始信息，尤其是名称、日期、数值、单位、代码、链接和来源。
- 批量输入应逐项处理，不要遗漏或擅自合并不同记录。
- 明确区分原始事实、用户观点、模型推断和待核实信息。
- 不编造缺失内容；无法确认的信息标记为“待补充”或“未核实”。
- 只有采集规则明确要求时才进行摘要、分析、评分或改写。
- 先检查当前工作区已有目录、记录和索引，再按照采集规则实际创建或修改工作区文件。
- 规则要求写入来源记录、索引、标签或其他文件时必须完成实际写入，不得只返回建议或草稿。
- 不修改规则来源文件，除非当前输入明确要求修改规则本身。
- 写入后执行规则要求的检查；最终回答只报告实际改动、验证结果、未核验内容和风险。

## 采集目标与处理规则
<Pin Markdown 快照>

## 当前输入
<用户原始输入>
```

Pin 使用入队时快照，而不是任务开始时重新读取。这样排队期间即使 Pin 被修改，本次任务的依据仍可追溯。界面应显示对应 Pin 哈希或更新时间。

这里的 Pin 不只代表一个主题，也可以定义字段、分类、事实核验和格式规则。通用提示词不得假定输入一定是文章或单条资料；例如项目资料库可能一次输入多个项目和链接，投资资料库可能输入必须原样保留日期、金额、单位和来源口径的原始数据。是否摘要、分析或评分由 Pin 明确决定。

## 7. 工作区与权限

采集模式现在是规则驱动的工作区执行器：

- `approvalPolicy` 使用不交互策略；
- `thread/start.sandbox` 使用 `workspaceWrite`；
- `turn/start.sandboxPolicy` 使用 `workspaceWrite`，并将 `writableRoots` 明确限制为入队时的当前任务工作区；
- `networkAccess` 为资料读取开启，但受本机 Codex 配置、组织策略和网络环境继续约束；
- 不授权写入工作区以外路径、破坏性操作或外部有副作用的动作。

每个采集 thread 使用入队时确认的工作区作为 `cwd`，因此该工作区的 `AGENTS.md` 等项目规则会生效。规则来源 Markdown 默认只读语义：CLI 可以读取它，但除非本次输入明确要求修改规则本身，否则不得改写该文件。

即使每个采集项都创建新 thread，也不能宣称模型“只有 Pin 上下文”：Codex 的系统级安全规则、账号策略、用户级配置和项目工作区指令仍会生效。

## 8. 执行报告与本地存储

采集产物就是规则在当前项目中要求创建或修改的真实文件，例如 `sources/` 记录、`indexes/projects.md` 和 `indexes/tags.md`。Chat Pin 不再额外创建 `collections/collection_<sessionId>.md`。

队列状态、规则快照、用户输入、错误和简洁执行报告保存在插件的 `.codex-pin-profile/collection-queue/`，不进入目标项目。执行报告由最终 agent message 组成，并附带 App Server `fileChange` 事件中可取得的路径元数据；它用于界面反馈和重试诊断，不是正式采集文档。

0.8.x 已生成的聚合文件属于用户数据。升级后不自动删除、迁移或覆盖这些文件。

## 9. 错误处理与恢复

| 场景 | 行为 |
| --- | --- |
| CLI 不存在或不可执行 | 不开启采集；显示检测到的路径、错误码、官方安装入口和重新检测 |
| App Server 不支持 | 提示升级 CLI，不退回原生 Desktop 对话 |
| CLI 未登录 | 保留队列，提示先在终端完成 Codex 登录后重试 |
| App Server 崩溃 | 当前项失败，等待项保留；重启后允许逐项重试 |
| Pin 在排队期间变化 | 当前项继续使用入队快照，新项使用新快照 |
| 用户切换任务 | 原任务模式保持启用但不接管新任务；返回原任务时恢复状态，队列与结果仍按原 session 归档 |
| 用户关闭采集 | 停止截获发送；已排队项继续执行。需要丢弃时由用户显式点击“清空” |
| 最终报告为空或 turn 失败 | 不标记完成，保存诊断并提供重试；已经发生的文件修改需在报告中核查 |

认证信息完全由 Codex CLI 管理。Chat Pin 不读取、复制或记录登录令牌。

## 10. 与修订模式的边界

| 项目 | 采集 | 修订 |
| --- | --- | --- |
| 目标 | 围绕 Pin 独立收集新材料 | 修改当前 Pin 文件 |
| 是否继承桌面对话 | 否 | 是，使用当前原生任务执行修改 |
| 发送路径 | Chat Pin 队列 -> CLI/App Server | 原生 Codex Desktop 发送 |
| 默认文件权限 | 当前任务工作区可写 | 工作区可写 |
| 输出位置 | 规则指定的来源、索引或其他项目文件 | 当前 Pin 文件 |
| 多次请求关系 | 每项新 thread，互不继承 | 围绕同一文件连续修订 |

两种模式不能同时开启，因为它们对发送按钮的含义相反。

## 11. 分阶段实现

### 阶段 A：后端探针

- 跨平台 CLI 解析与健康检查；
- App Server initialize/thread/start/turn/start 最小客户端；
- 用两个连续任务验证 threadId 不同且第二项不含第一项历史；
- 只输出到独立测试文件，不改 UI。

### 阶段 B：持久化队列

- FIFO、失败重试、显式清空和启动恢复；
- Pin 快照与哈希；
- 执行报告持久化和失败重试。

### 阶段 C：UI 接入

- “采集”按钮、互斥状态和队列计数；
- 可靠截获原生发送；
- 原生事件链继续前清空输入，入队失败且输入框仍为空时恢复输入；
- 执行报告与错误诊断。

### 阶段 D：兼容性验证

- Windows npm 安装、Windows Store 路径冲突；
- macOS npm/Homebrew 安装；
- CLI 未安装、未登录、旧版本、异常退出；
- 切换任务、切换 Pin、关闭启动器和重启恢复。

## 12. 验收标准

- 连续加入至少三个采集项，每项使用不同 threadId，并且结果不引用其他采集项的内容。
- 当前 Codex Desktop 任务的历史消息不会进入 App Server 请求。
- 采集开启时原生 Desktop 不会同时收到该条消息。
- 入队失败时输入不丢失；启动器重启后等待项仍可见。
- Pin 修改后，旧队列项仍能按原快照复现，新队列项使用新快照。
- 采集模式会按规则修改当前任务工作区，但默认不修改规则来源文件，也不能写出工作区。
- 规则要求创建来源记录和更新索引时，验收必须检查真实文件，而不是只检查最终回答文本。
- 修订与采集不能同时启用，切换任务后不会把请求送往旧 Pin。
- Windows 和 macOS 均通过 CLI 发现、启动、停止和失败提示测试；未实机验证的平台不得标为已支持。

## 13. 明确不在首版实现

- 修改 Codex Desktop 底层配置或聊天数据库；
- 清空、压缩或伪造原生任务历史；
- 把本地采集结果伪装成原生助手消息；
- 多队列并发执行；
- 自动安装、升级 CLI 或修改 PATH；
- 写入当前任务工作区以外的文件；
- 自动把所有采集结果再次总结成中心思想。该能力可在队列稳定后作为显式“整理”操作加入。
